# PROJECT_MANIFEST

> **Mask Platform** — платформа для генерации и производства многослойных
> физических масок/трафаретов для аэрографии и окраски сложных объектов.

```text
IMAGE → DIGITAL MASK PROJECT → MANUFACTURABLE MULTILAYER MASK → PRODUCTION FILES
```

---

## 1. Три главных утверждения

| # | Утверждение |
|---|---|
| 1 | **Главный объект системы — Mask Project**, не SVG и не картинка |
| 2 | **Главный технологический актив — Mask Engine**, не сайт |
| 3 | **Главный принцип — Design → Digital Manufacturing Model → Physical Mask** |

## 2. Философия в одном абзаце

Мы отделяем **дизайн** от **места нанесения**. Дизайн создаётся один раз,
привязывается к геометрии детали, хранится как цифровой паспорт
и воспроизводится в любой студии в любой момент. Через год, если деталь
повреждена, результат восстанавливается без участия автора.

**AI не отвечает за физическую корректность.** AI предлагает →
детерминированный геометрический движок распоряжается.

## 5. Ключевые инварианты

| # | Инвариант | Где проверяется |
|---|---|---|
| I-1 | У ревизии есть хотя бы один слой | ✅ `no_layers` → Fatal (`validate/src/lib.rs:335`) |
| I-2 | Номера слоёв уникальны в ревизии | ⚠️ нет БД; в фикстуре уникальность не проверяется |
| I-3 | Порядок слоёв определён | ⚠️ нет `LayerGraph`; `application_order` с fallback на `index` |
| I-4 | Каждый слой ссылается на существующую геометрию | ⚠️ нет БД; в фикстуре ссылка не проверяется |
| I-5 | `PASS` ⇒ нет `error`-нарушений | ✅ `Verdict::from_violations` + тест |
| I-6 | Manifest ⇔ есть артефакты | ✅ манифест строится из записанных артефактов |
| I-7 | Ревизия хранит снимки профилей | ⚠️ нет БД; профили читаются из файла по коду и версии |
| I-8 | Артефакты несут `engine_version` | ✅ `ArtifactContext.engine_version` |

**Обновлено 2026-10-06.** Таблица была написана, когда БД планировалась, и с тех пор
не сверялась. Три строки ссылались на механизмы, которых нет: `LayerGraph::validate`
(тип не существует в коде), «транзакция», «constraint», «FK». Решение A1 отложило
сервисный слой, поэтому эти инварианты не имеют носителя — и это надо видеть, а не
читать как «проверяется».

Что заменяет их сегодня:

* **I-3** — `LayerInput.application_order` с fallback на `index`
  (`validate/src/lib.rs:242`). Ацикличности как таковой нет: порядок — это число, а не
  граф, и конфликт разрешается правилом T-12 (пересечение слоёв с одинаковым
  `application_order` — error).
* **I-2, I-4, I-7** — проверяются на уровне загрузки фикстуры и профиля, но не
  принудительно. Это известный пробел, а не ложное обещание.

## 6. Технологические решения (зафиксированы)

| Решение | Обоснование |
|---|---|
| **Rust** — геометрическое ядро | Сложная геометрия, memory safety, WASM |
| **Go** — сервисы | HTTP, оркестрация, скорость разработки |
| **PostgreSQL** — метаданные | Транзакции, версии, связи |
| **S3** — артефакты | Большие объекты, версионирование |
| **Redis** — очередь и кэш | Достаточно для текущей нагрузки |
| **Next.js + React + TS** — фронтенд | Studio и платформа |
| **WASM** — браузерное ядро | Интерактивный preview без сервера |

Детали и альтернативы — в `docs/00_FOUNDATION/ADR_PROCESS.md`.

## 7. Чего проект не делает

| Не делает | Почему |
|---|---|
| Не продаёт «кусок плёнки» | Ценность в воспроизводимости, не в материале |
| Не начинает с сайта/маркетплейса | Сначала доказать производство |
| Не доверяет AI физическую корректность | П-01 |
| Не покупает оборудование до доказательства | Порядок: ПО → прогон → покупка |
| Не зашивает технологические числа в код | П-05 |
| Не растягивает картинку по размерам | см. `MODEL_FIT.md` |

## 8. Критерий успеха

> Взять достаточно сложное изображение, автоматически или полуавтоматически
> преобразовать его в многослойный Mask Project, **доказать производимость**
> и получить корректные файлы для физического изготовления.
> Затем физически изготовить и нанести на реальный объект.

Красивый сайт и AI-генерация картинок **не являются** критерием успеха.

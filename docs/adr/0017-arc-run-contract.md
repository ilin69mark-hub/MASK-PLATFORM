# ADR-0017 · Дуга в контуре заменяет ровно одно ребро

- **Status**: ACCEPTED
- **Date**: 2026-10-06
- **Deciders**: Founder / CTO
- **Affects**: `engine/kernel` (`geom.rs`, `canonical.rs`, `measure.rs`, `hash.rs`), `engine/wasm`, `engine/validate`, ADR-0004, ADR-0015
- **Principles**: P-03 (геометрия — источник истины), P-08 (воспроизводимость)
- **Supersedes**: —

## Context

`ArcSegment` документирован как хордальное представление прогона:

```rust
/// `from` and `to` index into [`Contour::points`]; `to` is exclusive, so the run is
/// `from .. to`.
```

Эта формулировка допускает дугу, покрывающую несколько рёбер. Проверка контура,
наоборот, требует, чтобы каждая дуга заменяла ровно одно последовательное ребро:

```rust
arc.to == (arc.from + 1) % n
```

Все потребители контура уже работали по второму правилу:

| Потребитель | Что делает | Где |
|---|---|---|
| `resolved_arcs` | Отбрасывает дугу, если `to != (from + 1) % n` | `geom.rs:278-293` |
| `flattened` | Подставляет аппроксимацию только при `arc.to == next` | `geom.rs:342-343` |
| `to_path_data` | Берёт список из `resolved_arcs` | `canonical.rs:130` |
| площадь / периметр | Берут список из `resolved_arcs` | `measure.rs:39`, `:126` |
| хеш | Берёт канонический path | `hash.rs:76`, `:82` |

Проблема в том, что математический помощник обходит контракт контура. Тест
`measure.rs:715-746` вызывает `arc_sweep` напрямую на дуге `from = 0, to = 2` и
проверяет свёртку в 270°. Это корректный тест чистой функции: помощник получает две
явно разрешённые точки и не проверяет контур. Но сам по себе тест выглядит как
утверждение, что многоточечные прогоны работают в полном контуре, — а они там не
работают и по ADR-0015 должны отвергаться.

До ADR-0017 несоответствие не было названо:

* тип разрешал прогон;
* проверка отвергала прогон;
* один тест проверял прогон напрямую.

«Просто разрешить прогоны везде» недостаточно, потому что это меняет площадь,
периметр, аппроксимацию и канонический path сразу в четырёх местах — то есть меняет
измерения, хеш и производство. «Просто запретить математику для прогонов» тоже
недостаточно: помощники принимают явные точки и по контракту не обязаны знать о
контуре.

## Decision

**`ArcSegment` остаётся структурой данных, допускающей произвольный прогон.
Но валидный контур в конвейере ядра принимает только дугу, заменяющую ровно одно
последовательное ребро.**

Другими словами:

* математический уровень (`arc_sweep`, `arc_segment_area`, `arc_length`) работает с
  явными конечными точками и не выполняет проверку контура;
* уровень контура (`Contour::validate`, `resolved_arcs`, `flattened`,
  `to_path_data` и все измерения) принимает только однореберные дуги;
* многоточечный прогон в контуре — это `GeometryError::ArcIndex`, а не молчаливое
  отбрасывание.

## Alternatives

### A. Разрешить многоточечные прогоны везде

- **Плюсы**: тип, математика и конвейер совпадают; исчезает отдельный класс
  «дуга есть, но её не видят».
- **Минусы**: меняет площадь, периметр, `flattened`, `to_path_data` и хеш.
  Разрешение прогона через промежуточные вершины требует решения, что делать с
  вершинами внутри дуги: удалять, сохранять или проверять. Разные ответы дают
  разную площадь — то есть меняют измерение, а не только контракт.
- **Стоимость**: M: согласованное изменение четырёх потребителей, тестов,
  фикстур и хешей.

### B. Сделать математику тоже однореберной

- **Плюсы**: единый контракт везде; невозможно вызвать помощник «неправильно».
- **Минусы**: помощники принимают явные точки именно для того, чтобы не зависеть от
  контура. Проверки границ там не к месту: у функции нет списка точек и нет
  понятия замкнутости. Это дублировало бы контракт контура в каждой функции.
- **Стоимость**: S, но с неверным распределением ответственности.

### C. Оставить как есть, без ADR

- **Плюсы**: ноль работы.
- **Минусы**: тип, проверка и один тест продолжают утверждать разное. Следующий
  читатель либо «исправит» проверку под тип, либо «исправит» тип под проверку —
  и оба варианта меняют измерения молча.
- **Стоимость**: нулевая сейчас, отказ в измерениях потом.
- **Почему отвергнут**: ложное соответствие между математикой и конвейером хуже
  явного разрыва.

## Consequences

### Positive

* Контракт назван там, где он действует: тип хранит дугу, контур проверяет дугу.
* Прямой тест `arc_sweep` перестаёт читаться как проверка многоточечной дуги в
  контуре, потому что это различие записано и закреплено тестом.
* Поведение не меняется: правило уже применяется в `Contour::validate` и
  покрыто отрицательным тестом `an_arc_spanning_several_edges_is_rejected`.

### Negative / Trade-offs

* В типе остаются значения, которые контур не принимает. Это намеренно: тип —
  структура данных, контур — валидированная сущность. Альтернатива — тип,
  который невозможно построить без контура — потребовала бы конструктора и
  переписала бы сериализацию.
* Тест многоточечной свёртки теперь нуждается в пояснении, иначе он будет
  выглядеть как контрпример к правилу.

### Follow-up

* Отдельная геометрическая схема для слоя (`BUG-005`, ADR-0016) должна ссылаться
  именно на контурный контракт, а не на сырой тип дуги.
* Если многоточечные прогоны когда-нибудь понадобятся производству, решение
  принимается отдельным ADR: что происходит с промежуточными вершинами и как это
  меняет площадь.

## Validation

Как проверяем, что решение верное. Критерий успеха:

1. `Contour::validate` отвергает `from = 0, to = 3` на четырёх точках как
   `GeometryError::ArcIndex` — покрыто тестом
   `an_arc_spanning_several_edges_is_rejected`.
2. `arc_sweep` на явных точках прежнего многоточечного теста возвращает прежние
   −270° — покрыто тестом `an_arc_wider_than_a_half_turn_is_measured_from_its_own_sweep`.
3. Оба теста существуют рядом и названы так, чтобы их различие было видно:
   один проверяет контур, другой — математику.
4. `make check` зелёный.
